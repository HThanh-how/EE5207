\chapter{Results}

\section{Implementation Summary}

Two RISC-V processor implementations were successfully completed:

\subsection{Milestone 2: Single-Cycle Processor}

The single-cycle RISC-V processor was successfully implemented with the following components:

\begin{itemize}
    \item \textbf{6 SystemVerilog modules}: All modules compile without errors. The design is partitioned into distinct units (ALU, register file, control, instruction memory, data memory, and top-level core), which simplifies debugging and future extensions.
    \item \textbf{41 instruction types}: All RV32I instructions (except FENCE) implemented. Each instruction class (arithmetic, logical, comparison, shift, load/store, branches, jumps, and upper-immediate) was mapped to a unique combination of control signals and ALU operations.
    \item \textbf{Memory-mapped I/O}: Complete I/O system with 6 peripheral types. The memory map follows the TA specification and allows test programs to communicate results via LEDs and seven-segment displays without any modification to the testbench.
    \item \textbf{16KB instruction memory}: Sufficient for test programs. This capacity covers all TA-provided ISA tests and leaves headroom for additional diagnostic programs.
    \item \textbf{2KB data memory}: Meets specification requirements. The data memory depth is enough to support stack usage, test data, and memory-mapped I/O pointers.
\end{itemize}

\subsection{Milestone 3: Pipelined Processor}

The pipelined RISC-V processor extends the single-cycle design with advanced features:

\begin{itemize}
    \item \textbf{Five-stage pipeline}: IF, ID, EX, MEM, WB stages with proper pipeline registers and control
    \item \textbf{Forwarding Unit}: Resolves data hazards by forwarding from MEM and WB stages to EX stage
    \item \textbf{Hazard Detection}: Detects and handles load-use hazards and control hazards
    \item \textbf{Two-bit Branch Predictor}: Dynamic branch prediction with 256-entry Branch Target Buffer (BTB)
    \item \textbf{BRAM-compatible memory}: 64~KiB synchronous instruction and data memory compatible with FPGA BRAM
    \item \textbf{Performance monitoring}: Debug signals (\texttt{o\_insn\_vld}, \texttt{o\_ctrl}, \texttt{o\_mispred}) for IPC and misprediction rate analysis
\end{itemize}

Overall, both implementations strictly follow the file structure and interface naming conventions required by the TA. This ensured that the processors could be dropped directly into the provided test environment without any wrapper logic or manual adjustments, reducing integration risk.

\section{Test Results}

\subsection{ISA Test Suite Results}

The processor successfully passed all required tests in the TA-provided test suite:

\begin{itemize}
    \item \textbf{Total Tests}: 41 instruction tests. Each test focuses on a particular instruction or group of closely related instructions.
    \item \textbf{Passed}: 40 tests (all except misaligned, which is optional). For every passing test, the scoreboard prints the test name followed by \texttt{PASS}.
    \item \textbf{Failed}: 0 required tests. During development, several early failures were observed, but they were all resolved by fixing control signals and immediate generation.
    \item \textbf{Optional Features}: Misaligned address handling (returns ERROR as expected). The TA-supplied test for misaligned access is expected to fail with \texttt{ERROR}, which matches the behavior of the current design.
\end{itemize}

\subsection{Test Execution}

The testbench correctly:

\begin{itemize}
    \item Loaded instruction memory from \texttt{isa.mem} (or fallback to \texttt{isa\_1b.hex}). This mirrors the TA environment and guarantees that the same binary is used for both reference and DUT runs.
    \item Executed all instructions sequentially, starting from reset PC and following the control flow dictated by branches and jumps.
    \item Monitored PC and LEDR outputs, which act as a compact summary of the processor state for the scoreboard.
    \item Displayed test results via scoreboard, comparing actual outputs against a golden model embedded in the TA testbench.
    \item Completed simulation successfully, terminating via \texttt{\$finish} only after all tests had been evaluated.
\end{itemize}

\section{Instruction Coverage}

All instruction types were verified:

\subsection{Arithmetic and Logical Instructions}

\begin{itemize}
    \item R-type: ADD, SUB, AND, OR, XOR - \checkmark All verified using register-to-register operations with diverse operand values (positive, negative, and boundary cases such as \texttt{0x7FFF\_FFFF}).
    \item I-type: ADDI, ANDI, ORI, XORI - \checkmark All verified with immediate values that exercise sign extension and bit-masking behavior.
    \item Comparison: SLT, SLTI, SLTU, SLTIU - \checkmark All verified, ensuring correct handling of signed vs. unsigned comparisons and edge cases around zero.
\end{itemize}

\subsection{Shift Instructions}

\begin{itemize}
    \item Logical shifts: SLL, SLLI, SRL, SRLI - \checkmark All verified with shift amounts from 0 to 31, confirming correct masking of the shift amount field.
    \item Arithmetic shift: SRA, SRAI - \checkmark All verified, particularly for negative operands, where the sign bit must be replicated.
\end{itemize}

\subsection{Memory Instructions}

\begin{itemize}
    \item Loads: LW, LH, LHU, LB, LBU - \checkmark All verified using patterns that distinguish between signed and unsigned behavior.
    \item Stores: SW, SH, SB - \checkmark All verified with write-read-back sequences to ensure that the correct bytes are modified in memory.
    \item Byte ordering: Little-endian - \checkmark Verified by observing how multi-byte values are stored and loaded in the waveform.
    \item Sign extension: Correct for signed loads - \checkmark Verified by loading negative values and checking that the upper bits are properly extended.
\end{itemize}

\subsection{Control Flow Instructions}

\begin{itemize}
    \item Branches: BEQ, BNE, BLT, BGE, BLTU, BGEU - \checkmark All verified using forward and backward branches, as well as taken and not-taken paths.
    \item Jumps: JAL, JALR - \checkmark All verified by confirming that the return address is correctly stored in \texttt{ra} and that the PC is redirected to the proper target.
    \item Upper immediate: LUI, AUIPC - \checkmark All verified to ensure that high-order bits and PC-relative offsets are formed exactly according to the ISA specification.
\end{itemize}

\section{Code Quality Metrics}

\subsection{Synthesizability}

\begin{itemize}
    \item All modules use synthesizable constructs such as \texttt{always\_ff} and \texttt{always\_comb} with clear reset behavior.
    \item No unsynthesizable operators in RTL code, for example no \texttt{\$display}, \texttt{\$finish}, or delays in the design hierarchy.
    \item Proper use of combinational and sequential logic, ensuring that latches are not inferred accidentally and that all state elements are clocked.
    \item No simulation-only constructs in design; such constructs are confined to the testbench.
\end{itemize}

\subsection{Design Modularity}

\begin{itemize}
    \item Clear separation of concerns, with datapath and control logic placed in different modules.
    \item Well-defined module interfaces that expose only necessary signals, making it easier to reuse modules in future pipelined designs.
    \item Reusable components (ALU, register file) that are parameterizable and can be instantiated in other processor variants.
    \item Easy to maintain and extend thanks to consistent naming conventions and extensive in-line comments.
\end{itemize}

\section{Performance Characteristics}

\subsection{Single-Cycle Processor}

While performance is not the primary goal of a single-cycle processor, the design demonstrates:

\begin{itemize}
    \item \textbf{Single-cycle execution}: All instructions complete in one clock cycle
    \item \textbf{Deterministic timing}: Fixed execution time for all instructions
    \item \textbf{Simple control}: Straightforward control unit logic
    \item \textbf{Baseline for comparison}: Foundation for pipelined implementation
\end{itemize}

\subsection{Pipelined Processor}

The pipelined processor achieves significant performance improvements:

\begin{itemize}
    \item \textbf{Throughput}: Up to 5 instructions in pipeline simultaneously (theoretical IPC = 1.0)
    \item \textbf{Forwarding}: Eliminates most data hazards without stalling, maintaining high IPC
    \item \textbf{Branch Prediction}: Reduces control hazard penalties through accurate prediction
    \item \textbf{Two-bit Predictor}: Achieves higher accuracy than static prediction, reducing misprediction rate
    \item \textbf{BRAM Memory}: Enables higher operating frequency compared to logic-based memory
\end{itemize}

\subsubsection{Performance Metrics}

The pipelined processor provides debug signals for performance analysis:

\begin{itemize}
    \item \textbf{IPC (Instructions Per Cycle)}: Calculated as \texttt{num\_insn / num\_cycle} from scoreboard
    \item \textbf{Misprediction Rate}: Calculated as \texttt{num\_mispred / num\_ctrl * 100\%} for branch instructions
    \item \textbf{Control Transfer Instructions}: Counted via \texttt{o\_ctrl} signal in WB stage
    \item \textbf{Valid Instructions}: Counted via \texttt{o\_insn\_vld} signal (excludes flushed instructions)
\end{itemize}

Expected performance improvements over single-cycle:
\begin{itemize}
    \item \textbf{IPC}: Typically 0.7--0.9 depending on program characteristics (vs. 1.0 for single-cycle, but single-cycle has much longer cycle time)
    \item \textbf{Misprediction Rate}: Typically 10--30\% depending on branch patterns (vs. 70\% for static not-taken prediction)
    \item \textbf{Frequency}: Higher maximum frequency due to shorter critical path in each pipeline stage
\end{itemize}

\section{Known Limitations}

\subsection{Single-Cycle Processor}

\begin{itemize}
    \item \textbf{Single-cycle execution}: Inefficient compared to pipelined designs
    \item \textbf{No cache}: All memory accesses go to main memory
    \item \textbf{Misaligned handling}: Basic truncation, not full support
    \item \textbf{No exception handling}: Processor does not handle exceptions
    \item \textbf{No interrupts}: No interrupt handling capability
\end{itemize}

\subsection{Pipelined Processor}

\begin{itemize}
    \item \textbf{Load-use hazards}: Still require one-cycle stall (cannot be resolved by forwarding)
    \item \textbf{Branch misprediction}: 3-cycle penalty when misprediction occurs
    \item \textbf{BTB size}: Limited to 256 entries, may cause conflicts for large programs
    \item \textbf{No cache}: All memory accesses go to main memory
    \item \textbf{Misaligned handling}: Basic truncation, not full support
    \item \textbf{No exception handling}: Processor does not handle exceptions
    \item \textbf{No interrupts}: No interrupt handling capability
\end{itemize}

These limitations are acceptable for educational processors and demonstrate understanding of fundamental processor design principles.
